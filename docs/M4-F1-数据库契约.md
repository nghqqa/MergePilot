# M4-F1 数据库契约 v2.8（实现基线）

> **v2.8 极窄勘误**：将 §9.2 的“RFC 8785 精确实现”收敛为 **MergePilot JCS Profile v1**。该 profile 在明确允许的输入域内遵循 RFC 8785/JCS 序列化，但因 PostgreSQL 16 `jsonb` 的表示边界而排除 `U+0000`，并要求在转为 `jsonb` 前 fail-closed 拒绝重复对象键、非法 Unicode 与 profile 外数字。表、角色、ACL、SD API 签名、确定性 ID 字段顺序、锁序、purge、revision binding 与 Controller 契约均不变。

> **权威性**：唯一权威来源。依据 M4-F0 writer-gate v5.10 + 直接读取的六个 `SKILL.md`/`run.py`/`schema/{input,output}.schema.json`（Skill 名以 `name`/`SKILL_NAME` 为准，**连字符**；目录下划线名不是 Skill 名）+ `skills/common/schema/{request,response}.envelope.schema.json` + `skills/common/runtime/errors.py` + 实际 `task_runs`/`run_pr_bindings` 字段。与 `m4f1_state.sql`/`tests/m4f1` 冲突以本文档为准。
>
> **v2.7 修订**：保留既有 status-aware output、registry、host-worker 信任边界、关系化 manifest、安全 purge 与“一 run 一 revision”；修复独立复审的两项 P2：`bind_revision` 采用 run_id 前置 reconcile + `ON CONFLICT DO NOTHING RETURNING` + 双键重读，所有不一致稳定映射 P0001、禁止泄漏 23505；首次 bind 定义 revision cut，bind 前允许本 run fixer head 刷新，bind 后由数据库 guard 禁止同 run 改 repo/pr/head，外部 PR head 漂移必须创建新 run，并将现有 Controller 就地更新路径列为实现阶段强制对齐。另明确 base-read RESULT 的 `git_sha` 必须非 NULL。
>
**实现状态**：schema、约束、角色、触发器、SD API 与 tests/m4f1 已对齐本契约；无待定字段。当前工作树尚未 commit/tag/push，正式发布状态仍待最终发布流程确认。

## 1. 设计原则
PostgreSQL 唯一权威；内容寻址；写只经 SECURITY DEFINER API；claim-based CAS+lease；原子完成；fail-closed+复合 FK；最小权限+双向 ACL 自检；全局锁顺序一致（§10）；**信任边界明确**（§6.2）；单一事务（失败整体回滚）。

## 2. 角色与 ACL
`controller`(=mergepilot,LOGIN)/`skill_runner`(LOGIN)/`snapshot_worker`(LOGIN)/`purge_operator`(LOGIN) 调用 SD；`runtime_owner`/`envelope_maint`/`gate_owner`(NO/NOINHERIT) 拥有 SD/触发器；既有 B4 角色不改。新角色 `NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOREPLICATION`；双向 membership=0。runtime 角色对 M4-F1 新表仅 SELECT + §3 SD EXECUTE，**无表级 INSERT/UPDATE/DELETE**（直接写→42501）；既有 Controller 对 B4 `run_pr_bindings` 的写权限仅用于 bind 前刷新，并受 revision guard 限制。**`skill_version_registry`/`revision_bindings` 不可变；runtime 无写权限**（仅迁移 seed / bind_revision SD 写）。

`gate_owner` 仅为 revision guard 获得 `SELECT ON revision_bindings`，不获该表或 `run_pr_bindings` 的 INSERT/UPDATE/DELETE；`_guard_bound_run_pr_revision()` 不向 runtime 角色授予 EXECUTE。

### 3.1 attempt 计数与 backoff
**attempts 仅在成功 claim 时 +1**（PENDING→LEASED 与过期重领）；heartbeat/fail/complete 不增；fail 按当前 attempts 判 retry/FAILED。`backoff(N):=LEAST(60, 2*POWER(2,N-1))` 秒（1→2s、2→4s、3→8s、4→16s、5→32s、6→60s）。max_attempts=3 逐次：claim(1)→fail→PENDING(2s)→claim(2)→fail→PENDING(4s)→claim(3)→fail→FAILED。

### 3.2 `enqueue_skill_job` —— request/manifest 不变量（经 snapshot_manifest_items）
单事务校验：① `(skill_name,skill_version)` ∈ registry；② `request_envelope_ref` content_type=完整 skill-request MIME 且解析为 JSON；③ common request 关系不变量（contract_version='1'、trace_id=p_trace_id、request_id 符合公式、input 存在、顶层键白名单 additionalProperties=false）；④ input schema 属 host worker 边界；⑤ **`(skill_name,skill_version,request_envelope_ref)` 必须 ∈ `snapshot_manifest_items` WHERE snapshot_id=p_snapshot_id**（精确 membership，§4.14），否则 P0001 `request not in snapshot manifest`；⑥ 建 skill_job_outbox(PENDING,attempts=0,next_retry_at=now())+skill_job_dependencies（递归 CTE 禁自/环）。

### 3.3 `bind_revision` / `enqueue_snapshot_job` —— 单 revision authority（v2.7）
`bind_revision(...)` 单事务按序执行：
1. `SELECT task_runs WHERE run_id=p_run_id FOR UPDATE`，要求 `skill_data_state='ACTIVE'`；PURGING/PURGED → P0001 `skill data is not ACTIVE`。该锁与 purge 串行化。
2. `SELECT run_pr_bindings WHERE run_id=p_run_id FOR SHARE`，校验 `repo/pr_number/head_sha` 与参数一致；缺失或不一致 → P0001 `revision binding mismatch`。
3. 读取 `mcp_calls.request_id=p_source_call_id`，要求 `phase='RESULT' AND decision='ALLOW' AND result_status='OK'`，且 `run_id=p_run_id`、`target_repo=p_repo`、`git_sha IS NOT NULL AND git_sha=p_base_sha`；否则 P0001 `revision provenance mismatch`。Controller 的 base-read Gateway/MCP 调用必须把权威 base commit SHA 写入该 RESULT 行的 `git_sha`；NULL 必须 fail-closed。
4. DB 重算 `source_evidence_digest:=sha256(canon(source_call_id,correlation_id,tool,target_repo,run_id,git_sha,result_status))`，要求等于参数；不匹配 → P0001 `revision evidence digest mismatch`。
5. 计算 `binding_id='rev-'||H_32(run_id,repo,pr_number,base_sha,head_sha,source_call_id,source_evidence_digest)`。先 `SELECT revision_bindings WHERE run_id=p_run_id`：存在且完整 immutable payload（binding_id/run_id/repo/pr/base/head/source_call/evidence digest；不含 recorded_at）一致 → 返回既有 binding_id；存在但 payload 不同 → P0001 `revision binding conflict`。不存在时执行 `INSERT ... ON CONFLICT DO NOTHING RETURNING binding_id`；未返回则按 run_id 与 binding_id 重读并比较完整 payload，一致 → 幂等返回，任一差异或 H_32 跨 run 碰撞 → P0001 `revision binding conflict`。不得向调用者泄漏 23505。

`enqueue_snapshot_job(p_run_id, p_revision_binding_id)`：要求 binding 属于该 run，从不可变 binding 读取 base/head/repo/pr；创建唯一的 `snapshot_job_id='snapjob-'||run_id`。一个 run 不接受第二个 revision。

**head 生命周期边界**：首次成功 `bind_revision` 是该 run 的 revision cut；在此之前，Controller 可把本 run fixer 产生并经 GitHub 读回的新 head 刷新到 `run_pr_bindings.head_sha`，这不构成外部漂移。bind 成功后，revision_bindings 保持该时点不可变快照；同 run 的 `run_pr_bindings.{repo,pr_number,head_sha}` 不得再发生实质变化。随后观察到不同 PR head 视为外部漂移：Controller 必须停止沿用该 run，并通过权威入口创建新 run，禁止执行现有 `controller.py:812` 的同 run 就地 UPDATE；旧 run/binding 保留审计且不得接收新 snapshot/skill job。

### 3.4 `complete_skill_job` —— status-aware output + digest 绑定（v2.7）
单事务（锁序 §10）：
1. `SELECT task_runs FOR SHARE` → `SELECT skill_job_outbox WHERE job_id+claim_id AND status='LEASED' AND lease_expires_at>now() FOR UPDATE`；未命中→步骤 9（幂等重放）。
2. response envelope 校验（§6.1：additionalProperties=false/17 required/类型/status-error_code 条件/与 job 一致）。
3. **(skill_name,skill_version,p_expected_output_schema_digest)** ∈ registry（§4.11 复合 FK 目标），否则 P0001。
4. **status-aware output 校验**（§6.3）：
   - `status∈{OK,PARTIAL}` ⇒ `p_output_schema_validated=true`（output 须已通过 Skill output schema）；否则 P0001。
   - `status=ERROR` 两类：(a) **structured error**：`p_output_schema_validated=true`（output 通过 Skill schema，可含 verdict）；(b) **generic runtime error**：`p_output_schema_validated=false`，标准 envelope output={}，verdict=NULL。
   - test-runner：`p_output_schema_validated=true` ⇒ output.verdict 必填 ∈{PASS,FAIL,TIMEOUT,ERROR}；`false` ⇒ verdict=NULL。
5. 派生+存响应：`put_envelope(response_bytes,'…skill-response.v1+json')`→output_digest；input_digest=job.request_envelope_ref；snapshot_manifest_digest 经 job.snapshot_id 查得。
6. invocation_id=`'inv-'||H(job_id,claim_id::text,32)`。
7. INSERT skill_invocations（expected_output_schema_digest、output_schema_validated、verdict 按规则）；PK 冲突→比完整 immutable payload，异→P0001。
8. CAS job LEASED→SUCCEEDED（不增 attempts），回填 result_invocation_id（DEFERRABLE）。返回 invocation_id。
9. 幂等重放：job SUCCEEDED+result_invocation_id→比 response_digest+payload，一致→既有，异→P0001。
> 调用方不得传 status/error_code/verdict/name/version（全从 response 解析+job 派生）；`p_expected_output_schema_digest`/`p_output_schema_validated` 由 **host worker 校验后**传入。

### 3.5 `complete_snapshot_job` —— 单事务原子（canonical manifest + revision + items 表）
单事务（锁序 §10）：
1. `SELECT task_runs FOR SHARE` → `SELECT snapshot_job_outbox WHERE job_id+claim_id AND status='LEASED' AND lease_expires_at>now() FOR UPDATE`；未命中→步骤 11。
2. 按 §7.2 对原始 `p_manifest_bytes` 执行 profile ingress（≤1MiB/严格 UTF-8/JSON、重复键/Unicode/数字域 fail-closed），通过后再解析并校验 manifest schema（§4.10）。
3. **revision 权威校验**：从 `revision_bindings`（job.revision_binding_id）读 SHA/repo/pr；校验 `manifest.{run_id,base_sha,head_sha}=binding`，不符→P0001 `revision sha mismatch`。
4. **manifest item 校验 + 排序**：每项 {kind:'skill-input',skill,skill_version,digest}；逐项 `EXISTS envelope_store WHERE content_digest=digest AND content_type='…skill-request.v1+json'` 且 `(skill,skill_version)`∈registry；同一 manifest 中 `(skill,skill_version)` 必须唯一（即使 digest 不同也拒绝），冲突→P0001 `duplicate manifest skill/version`；按 (skill UTF-16 序,skill_version,digest) 稳定排序。
5. canonicalize（§9.2）→ cb；`put_envelope(cb,'…snapshot-manifest.v1+json')`→manifest_digest=sha256(cb)。
6. snapshot_id=`'snap-'||H(run_id,base_sha,head_sha,manifest_digest,24)`。
7. INSERT/reconcile run_snapshots；PK 冲突→比完整 payload，异→P0001。
8. **派生 + 插 `snapshot_manifest_items`**：按排序后 items 逐行 INSERT（ordinal=0..n-1，skill_name,skill_version,request_envelope_ref=digest）；ON CONFLICT（snapshot_id,skill_name,skill_version）DO NOTHING；**比较 JSON items 与关系行完全一致**（数量、字段、顺序），不一致→P0001 `manifest item relational mismatch`。因此同一 snapshot 同一 Skill/version 的第二个 digest 不能形成第二行。
9. CAS snapshot_job LEASED→SUCCEEDED（不增 attempts），回填 snapshot_id；`p_set_active AND active_snapshot_id IS NULL`→UPDATE task_runs。返回 snapshot_id。
10. 幂等重放：重 canonicalize+派生 items→比 manifest_digest 与 items 完整一致→既有 snapshot_id；异→P0001。

### 3.6 claim / heartbeat / fail
claim：校验 lease 范围；锁 task_runs FOR SHARE→job FOR UPDATE；PENDING(`next_retry_at<=now() AND attempts<max_attempts`，skill 全依赖 SUCCEEDED)→LEASED（attempts+1，新 claim_id）；LEASED 过期+attempts<max→重领（attempts+1，新 claim_id）；LEASED 过期+attempts≥max→原子 FAILED+NULL；其它→NULL。heartbeat：lease 范围；CAS lease_expires_at>now()；不改 attempts。fail：lease 范围；同 CAS；不改 attempts；attempts<max→PENDING+next_retry_at=backoff(attempts)，否则 FAILED。

## 4. 逐表字段定义

### 4.1 `envelope_store`（内容寻址，不可变；§7）
content_digest TEXT PK CK(64hex)=sha256(content_bytes)；content_bytes BYTEA NN；content_json JSONB（派生）；content_type TEXT NN CK IN(3 完整 MIME)；size_bytes INTEGER NN CK(<=1048576 AND =octet_length)；created_at。触发器 trg_envelope_immutable（_immutable_except_purge）+ trg_envelope_digest_check。

### 4.2 `run_snapshots`（不可变）
snapshot_id PK；run_id FK；repo/pr_number NN（=revision_bindings）；base_sha/head_sha NN CK(40hex)（=binding）；manifest_digest NN FK→envelope_store；incomplete BOOLEAN default false；created_at。UQ (run_id,manifest_digest)、(run_id,snapshot_id)。触发器 trg_gate_run_snapshots + trg_run_snapshots_immutable。**写入只经 complete_snapshot_job**。

### 4.3 `snapshot_job_outbox`（claim_id CAS + revision_binding_id）
job_id PK（'snapjob-'||run_id）；run_id FK；snapshot_id 复合 FK；revision_binding_id NN FK→revision_bindings；idempotency_key UQ；status CK(PENDING/LEASED/SUCCEEDED/FAILED)；claim_id UUID；leased_by/lease_expires_at/last_heartbeat_at；attempts/max_attempts/next_retry_at default 0/3/now()；error；created_at/claimed_at/completed_at。触发器 trg_gate_snapshot_job_outbox。

### 4.4 `skill_job_outbox`（claim_id CAS；循环 FK §11；registry 复合 FK）
job_id PK（§9）；run_id FK；snapshot_id 复合 FK；trace_id；skill_name/skill_version **复合 FK (skill_name,skill_version)→skill_version_registry**；attempt CK(>=1)；request_envelope_ref FK→envelope_store；idempotency_key UQ；status CK(PENDING/LEASED/SUCCEEDED/FAILED)；claim_id UUID；leased_by/lease_expires_at/last_heartbeat_at；attempts/max_attempts/next_retry_at default 0/3/now()；result_invocation_id FK→skill_invocations ON DELETE SET NULL DEFERRABLE；error；created_at/claimed_at/completed_at。触发器 trg_gate_skill_job_outbox。

### 4.5 `skill_job_dependencies`
job_id/depends_on_job_id FK→skill_job_outbox ON DELETE CASCADE；PK(job_id,depends_on_job_id)；CHECK(job_id<>depends_on_job_id)。多依赖；enqueue 递归 CTE 禁环；claim 校验全依赖 SUCCEEDED。

### 4.6 `skill_invocations`（不可变；status-aware + digest 绑定；v2.7）
invocation_id PK；run_id FK；snapshot_id 复合 FK；job_id FK→skill_job_outbox ON DELETE CASCADE；trace_id/skill_name/skill_version/attempt（=job）；request_id；contract_version default '1' CK('1')；status CK(OK/PARTIAL/ERROR)；error_code CK(7 码；status=ERROR⇒NOT NULL)；verdict CK IN(PASS,FAIL,TIMEOUT,ERROR) nullable；input_digest FK→envelope_store（=job.request_envelope_ref）；output_digest FK→envelope_store；snapshot_manifest_digest FK→envelope_store；**expected_output_schema_digest TEXT NN**（原 output_schema_digest 改名）；**output_schema_validated BOOLEAN NN**；duration_ms；started_at/finished_at；idempotency_key UQ。
**复合 FK `(skill_name,skill_version,expected_output_schema_digest)`→skill_version_registry**（§4.11 对应 UNIQUE）。
**CK（status-aware 一致性）**：
- `status IN ('OK','PARTIAL') ⇒ output_schema_validated=true`
- `output_schema_validated=false ⇒ verdict IS NULL`
- `status='ERROR' AND error_code IS NULL` 禁止；`status∈{OK,PARTIAL} AND error_code IS NOT NULL` 禁止。
触发器 trg_gate_skill_invocations + trg_skill_invocations_immutable。

### 4.7 `task_runs`（扩展列）
既有列不变。新增 trace_id NULL；active_snapshot_id NULL（复合 FK；仅 complete_snapshot_job 设/advance_purge 清）；skill_data_state NN default 'ACTIVE' CK(ACTIVE/PURGING/PURGED)。触发器 trg_transition（_enforce_transition：仅 envelope_maint CAS）。

### 4.8 `purge_requests`（单一模型）
purge_id PK；run_id FK；target_state NN CK IN('PURGED')；status NN default 'REQUESTED' CK IN('REQUESTED','PURGING','PURGED')；requested_by；requested_at default now()；purging_at/completed_at；error。部分唯一 UNIQUE(run_id) WHERE status IN('REQUESTED','PURGING')。

### 4.9 `rollback_runs`（既有，引用；不改）
trg_gate_rollback_runs（key 不可变+稳定序 FOR KEY SHARE）。

### 4.10 snapshot manifest 内容契约（pre-run 输入快照；item 含 skill_version；稳定排序）
```json
{ "manifest_version":"1","run_id":"<run_id>","base_sha":"<40hex>","head_sha":"<40hex>",
  "produced_at":"<ISO8601 UTC>",
  "items":[{"kind":"skill-input","skill":"<6 名>","skill_version":"1.0.0","digest":"<64hex>"},...] }
```
仅 skill-input；items 按 (skill UTF-16 序,skill_version,digest) 稳定排序；禁重复。每项 digest∈envelope_store 且 content_type=skill-request、(skill,skill_version)∈registry。

### 4.13 `revision_bindings`（v2.7：一 run 一 revision + 可验证 provenance）
```
revision_bindings(
  binding_id TEXT PRIMARY KEY,             -- 'rev-'||H_32(run_id,repo,pr_number,base_sha,head_sha,source_call_id,source_evidence_digest)
  run_id TEXT NOT NULL UNIQUE REFERENCES task_runs(run_id),
  repo TEXT NOT NULL, pr_number INTEGER NOT NULL,
  base_sha TEXT NOT NULL CHECK (base_sha ~ '^[0-9a-f]{40}$'),
  head_sha TEXT NOT NULL CHECK (head_sha ~ '^[0-9a-f]{40}$'),
  source_call_id TEXT NOT NULL REFERENCES mcp_calls(request_id), -- Gateway/MCP RESULT 审计行
  source_evidence_digest TEXT NOT NULL CHECK (64hex),  -- 该调用证据 sha256
  recorded_at TIMESTAMPTZ NOT NULL DEFAULT now())
```
**不可变且一 run 一 revision**：`trg_revision_bindings_immutable` 对 UPDATE/DELETE 全拒，`UNIQUE(run_id)` 保证一个 run 只能绑定一个 revision；首次 bind 后发现外部 PR head 漂移必须创建新 run；bind 前本 run fixer head 刷新按 §3.3 允许。`bind_revision` 是唯一写入口，强制 run 为 ACTIVE，校验 `run_pr_bindings`，并验证成功的 Gateway/MCP RESULT `mcp_calls(request_id)` 及 DB 重算的 evidence digest。`binding_id` 按 §9.6 确定性生成：同 run 同完整 payload 重放返回既有 binding_id；同 run 异 payload → P0001 `revision binding conflict`。**base_sha 不在 run_pr_bindings**，必须由 Controller 经 Policy Gateway/MCP read 取得并记录 `source_call_id/source_evidence_digest`；DB 不自行验证 GitHub 外部事实，只验证导入证据的 provenance 与摘要。revision binding 是**永久审计元数据**：skill-data purge 不删除，但 PURGING/PURGED 后禁止新增。

冲突处理必须采用 §3.3 step 5 的显式 reconcile：先按 run_id 比较完整 immutable payload，再以 `INSERT ... ON CONFLICT DO NOTHING RETURNING` + 双键重读处理并发或 H_32 碰撞；任何不一致统一映射 P0001 `revision binding conflict`，禁止泄漏 UNIQUE 的 23505。

`trg_run_pr_bindings_revision_guard`：`BEFORE UPDATE OF repo,pr_number,head_sha ON run_pr_bindings`，调用 `gate_owner` 持有的 `_guard_bound_run_pr_revision()`（SECURITY DEFINER、`SET search_path=pg_catalog`、全限定 `public.*`、`REVOKE ALL FROM PUBLIC`）。若该 run 尚无 revision_binding，则允许 Controller 在 bind 前刷新 fixer 产生并读回的 head；若已存在 binding，仅允许三字段值均未发生实质变化的幂等 UPDATE，任一 `IS DISTINCT FROM OLD` → P0001 `revision already bound`。该触发器是 Controller 对齐的数据库兜底；Controller 仍必须在 bind 后发现外部 head 漂移时创建新 run，不得依赖触发器异常作为正常控制流。

### 4.14 `snapshot_manifest_items`（v2.7：规范化且每 Skill/version 唯一）
```
snapshot_manifest_items(
  snapshot_id TEXT NOT NULL REFERENCES run_snapshots(snapshot_id) ON DELETE CASCADE,
  ordinal INTEGER NOT NULL CHECK (ordinal >= 0),
  skill_name TEXT NOT NULL, skill_version TEXT NOT NULL,
  request_envelope_ref TEXT NOT NULL REFERENCES envelope_store(content_digest),
  PRIMARY KEY (snapshot_id, ordinal),
  UNIQUE (snapshot_id, skill_name, skill_version),
  FOREIGN KEY (skill_name, skill_version) REFERENCES skill_version_registry(skill_name, skill_version))
```
ordinal = (skill UTF-16 序, skill_version, request_envelope_ref) 稳定排序位（complete_snapshot_job 赋值）。同一 snapshot 的 `(skill_name,skill_version)` 仅允许一个 request；重试复用同一 job/request，不预建第二份 input。complete 同事务派生+插入+比对 JSON items 与关系行完全一致；enqueue_skill_job 经此表验精确 membership。

## 5. 状态转换与事务边界
### 5.1 skill_data_state
ACTIVE→PURGING→PURGED（仅 envelope_maint 经 advance_purge）。
### 5.2 outbox 状态机（claim_id+lease+next_retry_at；attempt 仅 claim+1）
PENDING(`next_retry_at<=now() AND attempts<max_attempts`)→LEASED（attempts+1）；LEASED(过期)+attempts<max→LEASED(重领,attempts+1,新 claim_id)；LEASED(过期)+attempts≥max→FAILED+NULL；LEASED→LEASED(heartbeat)；LEASED→SUCCEEDED(complete)；LEASED→PENDING/FAILED(fail,按当前 attempts)。heartbeat/complete/fail 须 lease_expires_at>now()；p_lease_seconds∈1..3600。
### 5.3 ERROR 映射（v2.7 status-aware）
有合法 response envelope：OK/PARTIAL/structured-ERROR→complete+invocation（output_schema_validated=true）；generic-runtime-ERROR（标准 output={}）→complete+invocation（output_schema_validated=false, verdict=NULL）。无任何 envelope（基础设施失败）→fail_skill_job，无 invocation。
### 5.4 事务边界与幂等
complete_skill_job/complete_snapshot_job 单事务；commit 前 crash→整回滚；commit 后返回丢失→幂等重放（比 digest+完整 payload，异→P0001）。advance_purge 单事务失败整体回滚。

## 6. 校验边界与信任边界
### 6.1 response envelope（complete_skill_job 体内硬编码）
`p_response_bytes` 先按 §7.2 执行 profile ingress（≤1MiB/严格 UTF-8/JSON、重复键/Unicode/数字域 fail-closed）；通过后再校验顶层键⊆白名单（additionalProperties=false）、17 required、类型、status/error_code 条件，以及 name=job.skill_name、version=job.skill_version、trace_id、request_id 一致。
### 6.2 信任边界（v2.7 冻结）
- **完整 JSON Schema 校验（input/output）由 host skill worker 执行**（M4-A runtime jsonschema）；DB 不重新实现。
- **凭据隔离**：DB 连接凭据 / skill_runner token **不得**进入 Skill subprocess/container、request envelope、环境变量、artifact、stdout/stderr。Skill 执行环境与 DB 凭据严格隔离。
- **仅 host worker 在完成 schema 校验后调用 `complete_skill_job`**（传入 expected_output_schema_digest + output_schema_validated）。
### 6.3 status-aware output 规则（v2.7）
- `status∈{OK,PARTIAL}`⇒`output_schema_validated=true`（output 通过 Skill output schema）。
- `status=ERROR`：(a) structured⇒`output_schema_validated=true`（output 通过 schema，可含 verdict）；(b) generic runtime⇒`output_schema_validated=false`，标准 output={}, verdict=NULL。
- test-runner：`output_schema_validated=true`⇒verdict∈{PASS,FAIL,TIMEOUT,ERROR} 必填；`false`⇒verdict=NULL。
- DB CK 强制：`status∈{OK,PARTIAL}⇒validated=true`；`validated=false⇒verdict IS NULL`。

## 7. envelope_store 限制 / 校验 / 派生 / ERROR 策略
### 7.1 content_type CK（完整冻结 MIME）
`application/vnd.mergepilot.skill-request.v1+json`、`application/vnd.mergepilot.skill-response.v1+json`、`application/vnd.mergepilot.snapshot-manifest.v1+json`。
### 7.2 size≤1048576；MergePilot JCS Profile v1 ingress；content_json 派生（v2.8）
`put_envelope` 对三种 MIME 使用同一 fail-closed 两阶段入口。第一阶段在任何 `jsonb` 转换或持久化之前验证原始 `BYTEA`：大小 `1..1048576`、严格 UTF-8、JSON syntax、所有层级对象属性名唯一、无 `U+0000`、无 lone surrogate，且所有数字属于 §9.2 的 profile。重复键按解码后的属性名判断，因此 `{"a":1,"\u0061":2}` 也必须拒绝；禁止依赖 `jsonb` 的 last-key-wins 行为。稳定错误为 P0001，message fragment 分别为 `invalid UTF-8 or JSON`、`duplicate object key`、`U+0000 not allowed`、`invalid Unicode scalar`、`number outside MergePilot JCS profile`。

第二阶段仅在第一阶段成功后派生 `content_json JSONB`、`content_digest=sha256(content_bytes)` 与 `size_bytes`，再执行不可变内容寻址 reconcile。`canonical_json(jsonb)` 只能处理已经通过第一阶段验证的数据；skill request、skill response、snapshot manifest 均不得绕过该入口。相同 digest 的重放必须比较完整 immutable payload，不得以裸 `ON CONFLICT DO NOTHING` 视为成功。
### 7.3 标准 ERROR envelope 策略
Skill 产出超限/不可序列化→构造标准 ERROR envelope 写入（output_schema_validated=false, output={}, verdict=NULL）；基础设施失败（无 envelope）→fail_skill_job。

## 8. purge 事务顺序（v2.7：revision binding 永久保留）
`revision_bindings` 不属于 skill data，不进入候选 digest C，也不参与任何 DELETE；purge 成功后永久保留该 run 的 revision/provenance 审计链。`bind_revision` 在取得 `task_runs FOR UPDATE` 后仅接受 ACTIVE，因此 PURGING/PURGED 状态下必拒绝，且不得留下半插入或 orphan binding。
`advance_purge` 单事务：① `SELECT task_runs WHERE run_id FOR UPDATE` → ② **捕获候选 digest C**（含 `skill_invocations.{input,output,snapshot_manifest}_digest` + `skill_job_outbox.request_envelope_ref` + `run_snapshots.manifest_digest` + **`snapshot_manifest_items.request_envelope_ref`**） → ③ `UPDATE task_runs SET active_snapshot_id=NULL` → ④ CAS REQUESTED→PURGING + skill_data_state ACTIVE→PURGING → ⑤ 删 skill_job_outbox(CASCADE→skill_invocations/dependencies)、snapshot_job_outbox、**run_snapshots（CASCADE→snapshot_manifest_items）** → ⑥ **`DELETE envelope_store WHERE content_digest=ANY(C) AND NOT EXISTS（全库 skill_invocations/skill_job_outbox/run_snapshots/snapshot_manifest_items 任何引用）`**（跨 run/snapshot 共享 digest 不删）→ ⑦ CAS PURGING→PURGED + skill_data_state PURGING→PURGED。任一失败→整回滚。writer-gate 在 PURGING 下允许受控删除（触发器 BEFORE INSERT OR UPDATE 不触发 DELETE；_immutable_except_purge 放行 envelope_maint）。

## 9. 确定性 ID / canonical JSON / backoff
### 9.1 canon() —— 长度前缀，NULL 独立标记，byte length，UTF-8，固定字段序
NULL→`-1:`；非 NULL→`octet_length(v::text::bytea)||':'||v::text`。`H_n(x):=left(encode(digest(canon(x)::bytea,'sha256'),'hex'),n)`。
### 9.2 canonical_json —— MergePilot JCS Profile v1（v2.8）
该 profile 对允许输入域使用 RFC 8785/JCS canonical serialization，但不宣称覆盖 RFC 8785 的完整理论输入域。允许值为 `null`、boolean、string、array、object 与 profile number；入口必须是有效 UTF-8/I-JSON，对象属性名在每一层唯一。`U+0000`、lone surrogate、重复键及 profile 外数字在转为 `jsonb` 前以 P0001 拒绝。重复键本身不是合法 JCS 输入；PostgreSQL `jsonb` 静默合并重复键的行为不得用作验证或规范化。

对象属性名按 **UTF-16 code unit 序**。字符串使用 JCS §3.2.2.2：`U+0008→\b`、`U+0009→\t`、`U+000A→\n`、`U+000C→\f`、`U+000D→\r`，quote→`\"`，backslash→`\\`，其余 `U+0000..U+001F` 使用小写 `\u00xx`，其他 Unicode scalar 原样输出。

数字先映射到有限 IEEE-754 binary64，再按 ECMAScript/JCS 最短 round-trip 形式序列化；`-0→0`，指数使用小写 `e`、无多余前导零，正指数按规范保留 `+`，定点/科学计数边界遵循 ECMAScript。整数语义值须满足 `|n|≤2^53`，超界以 P0001 拒绝，因此 `1e21` 在本 profile 中是超范围整数而非合法输出向量。非有限、float8 溢出或不可表示值同样拒绝。禁止以 PostgreSQL `float8::text`、Python `repr/str(float)` 或默认 `json.dumps` 直接冒充 JCS NumberToString。

`D_in=sha256(canonical_json(request.input))`；§9.6 的 `request_id` 字段顺序与公式不变，其中 `canonical_json` 专指本 profile。PG 与独立实现必须分别等于固定规范 canonical bytes/hex/SHA；二者彼此相等但不等于规范常量时仍为 FAIL。

### 9.3 测试向量（原始输入；固定规范常量为 oracle）
合法向量：V1 `{"b":1,"a":{"n":null}}`；V2 `{"z":"é","a":"α"}`；V3 `{"c":1.0,"b":1.50e2,"a":-0.0}`；V4 `[1,null,{"b":2,"a":1}]`；**V5 `{"":1,"𝕏":2}`（U+E000 与 U+1D54F；UTF-16 序 𝕏<U+E000，UTF-8 字节序相反）**；V6 `{"a\\b":"x\ty"}`；V7 `{"n":1e2}`；V8 `{"n":-0}`。拒绝向量：V9 `{"n":9007199254740993}`（2^53+1）。另须覆盖短转义、其他控制字符、`1e-7→1e-7`、`1e-6→0.000001`、重复键、escaped-equivalent 重复键、`U+0000`、lone surrogate、非有限与溢出。expected 禁止由被测 PG helper 或同构手写算法动态生成。
### 9.4 retry backoff
`backoff(N):=LEAST(60, 2*POWER(2,N-1))` 秒，N=当前 attempts。序列 1→2s…6→60s。overflow 截断 60s。
### 9.5 两种 digest
D_in=canonical_digest(request.input)；D_req=sha256(request_envelope_bytes)。
### 9.6 ID 公式
request_id=`'req-'||H_24(trace_id,run_id,skill_name,attempt::text,D_in)`；skill_job job_id/idempotency=`'sj-'||H_32(run_id,coalesce(snapshot_id,''),skill_name,skill_version,attempt::text,D_req)`；invocation_id=`'inv-'||H_32(job_id,claim_id::text)`；snapshot_id=`'snap-'||H_24(run_id,base_sha,head_sha,manifest_digest)`；snapshot_job job_id=`'snapjob-'||run_id`；purge_id=`'pur-'||H_24(run_id,requested_by,requested_at::text)`；**binding_id=`'rev-'||H_32(run_id,repo,pr_number,base_sha,head_sha,source_call_id,source_evidence_digest)`**；claim_id=gen_random_uuid()。所有冲突比较完整 immutable payload；禁止裸 `ON CONFLICT DO NOTHING`。

## 10. 全局锁顺序
**task_runs → run_pr_bindings/outbox job → mcp_calls/snapshot/invocation**。`bind_revision`：task_runs FOR UPDATE → run_pr_bindings FOR SHARE → mcp_calls read → revision_bindings insert/reconcile；complete_*/claim/heartbeat/fail：task_runs FOR SHARE → job_outbox FOR UPDATE → 子表；advance_purge：task_runs FOR UPDATE → 删 skill data 子表，但不删 revision_bindings。所有入口先锁 task_runs，bind 与 purge 串行化（并发反例 §12）。

Controller bind 前刷新 `run_pr_bindings` 时沿用已存在的 `task_runs FOR UPDATE → run_pr_bindings UPDATE` 顺序；revision guard 只读 revision_bindings，不反向获取 task_runs。bind 后外部 head 漂移走新 run，不在旧 run 上重试 UPDATE。该顺序与 `bind_revision`、purge 共用 task_runs 首锁，不形成反向锁边。

## 11. 外键删除策略
### 11.1 循环 FK（skill_job_outbox↔skill_invocations）
skill_invocations.job_id→skill_job_outbox(job_id) ON DELETE CASCADE；skill_job_outbox.result_invocation_id→skill_invocations(invocation_id) ON DELETE SET NULL DEFERRABLE。
### 11.2 task_runs.active_snapshot_id 复合 FK
(run_id,active_snapshot_id)→run_snapshots(run_id,snapshot_id)；purge 先 NULL 化再删 run_snapshots；失败整体回滚。
### 11.3 snapshot_manifest_items
snapshot_id→run_snapshots ON DELETE CASCADE（删 snapshot 级联删 item）；request_envelope_ref→envelope_store；(skill_name,skill_version)→registry；`UNIQUE(snapshot_id,skill_name,skill_version)` 保证每个 snapshot 的每个 Skill/version 只有一个 request。
### 11.4 跨 run 复合 FK / 内容寻址 FK / registry 复合 FK
run/snapshot/job 复合 FK；digest→envelope_store（purge 引用计数删除含 snapshot_manifest_items）；skill_job_outbox (skill_name,skill_version)→registry PK；skill_invocations (skill_name,skill_version,expected_output_schema_digest)→registry UNIQUE。
### 11.5 revision_bindings provenance 与保留
`run_id UNIQUE REFERENCES task_runs(run_id)` 冻结一 run 一 revision；`source_call_id REFERENCES mcp_calls(request_id)` 将导入 revision 绑定到 Gateway/MCP RESULT 审计行。revision_bindings 不级联删除、不属于 skill-data purge 范围，UPDATE/DELETE 由 immutable trigger 拒绝；PURGING/PURGED 只禁止新增，不影响既有绑定的永久审计可读性。
`trg_run_pr_bindings_revision_guard` 以 revision_bindings 的存在性定义 cut：cut 前允许现有 Controller 刷新 run_pr_bindings；cut 后拒绝 repo/pr/head 实质变化。revision_bindings 不反向跟随或覆盖更新，旧 run 的两份审计记录保持 bind 时点一致。

## 13. 与现行 m4f1_state.sql 的差异（文档为准；后续阶段对齐，本轮不改）
相对现行 SQL，v2.8 要求：
1. status-aware output（OK/PARTIAL⇒validated；ERROR structured/generic-runtime；output_schema_validated BOOL NN；output_schema_digest→expected_output_schema_digest；test-runner verdict 仅 validated 时必填）。
2. skill_version_registry 重构（PK(skill,version)、input+output digest NN、UNIQUE、复合 FK；实测 12 digest；不可变）。
3. 信任边界（host worker 校验；DB 凭据隔离；仅校验后调 complete）。
4. snapshot_manifest_items 表（complete 同事务派生+比对；enqueue 经该表验 membership）。
5. purge 候选含 items.request_envelope_ref；CASCADE 删 items；删 envelope 查全引用（含 items）；跨 snapshot 共享不删。
6. revision_bindings 改为 `run_id UNIQUE`，新增 `source_call_id FK→mcp_calls(request_id)` 与 source_evidence_digest；`bind_revision` 仅接受 ACTIVE，并校验成功 RESULT 的 phase/decision/result_status/run/repo/非 NULL git_sha 及 DB 重算摘要。
7. bind_revision 按 run_id 前置 reconcile，并以 `ON CONFLICT DO NOTHING RETURNING` + 双键重读兜底；同 payload 重放、同 run 异 payload或 H_32 碰撞统一 P0001，不泄漏 23505。
8. revision binding 永久保留，不纳入 skill-data purge；PURGING/PURGED 后禁止新增。
9. snapshot_job_id 固定为 `snapjob-<run_id>`、active_snapshot_id 只设置一次；`snapshot_manifest_items` 改为 `UNIQUE(snapshot_id,skill_name,skill_version)`。
10. 一 run 一 revision 以首次 bind 为 revision cut：bind 前允许本 run fixer head 刷新；bind 后 `trg_run_pr_bindings_revision_guard` 禁止同 run 改 repo/pr/head，外部 PR head 漂移必须创建新 run。现有 `controller.py:811-812` 就地更新路径必须在实现阶段对齐。
11. bind_revision 锁序、provenance/evidence/23505 反例、revision cut/head 漂移、purge 并发与每 Skill/version 单 request 反例纳入验收。
12. 新增 gate_owner 持有的 revision guard 触发器函数及最小 `SELECT ON revision_bindings`；PUBLIC/runtime 无 EXECUTE，gate_owner 无相关表 DML。
13. `put_envelope` 在 `jsonb` 转换前执行 MergePilot JCS Profile v1 ingress；`canonical_json` 仅处理已验证的 profile 数据；固定规范常量而非被测实现互相比较是 canonicalization 的发布门禁。
