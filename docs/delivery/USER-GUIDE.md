# MergePilot 用户指南（审查者 / 维护者视角，rc.35.4 交付口径）

> 面向受邀成员的日常使用。部署与配置见 [DEPLOY-GUIDE.md](DEPLOY-GUIDE.md)；
> 出错先查 [TROUBLESHOOTING.md](TROUBLESHOOTING.md)。
> 边界一句话：**补丁永远是建议；系统不自动改代码、不自动合并、不设 required check；
> 一切远端写（目前仅 PR 评论发布）需维护者逐次人工确认。**

## 1. 登录与身份确认

1. 打开 Console（管理员提供的地址），登录页选 **GitHub** 或 **Gitee**。登录为**邀请制**：
   仅事先被按平台数字 id 邀请的成员可登录（无公共注册）。
2. 登录后确认顶栏「身份 · 组织 · 角色」。角色决定你能做什么：

| 角色 | 能做什么 |
|---|---|
| **维护者（maintainer）** | 查看、触发审查、**审批修复票**、**PR 裁定**、**发布审查评论**、绑定/解绑仓库、发起修复 |
| **审查者（reviewer）** | 查看、触发审查、对发现提交反馈 |
| **贡献者（contributor）** | 基础查看（仓库/PR/代码/RAG 检索） |
| **平台管理员（platform_admin）** | 成员/数据源/设置/出站策略。**刻意无审批、无裁定、无发布权**（平台管理与审查裁定分离） |
| **审计员（auditor）** | 仅审计元数据只读（不可读代码/RAG 内容） |

按钮权限即权限矩阵的投影：无权限的按钮置灰并在下方给出具体原因（如
「当前角色无 decide_review」）——这是权限设计，不是故障。

## 2. 仓库接入

- **GitHub**：仓库页 →「安装 / 更新 GitHub App」→ 在 GitHub 选择账号与仓库 → 回跳 → 选择仓库**绑定**。
  GitHub App 对你的仓库是**只读**（Metadata/Contents/Pull requests/Checks/Commit statuses 五项全部 Read-only）。
- **Gitee**：仓库页建立 Gitee 连接（部署级 PAT）→ 绑定仓库。
- 绑定后，PR 新开/更新（webhook）自动触发审查，无需手动点。
- 手动重审：PR 详情页「触发审查」（reviewer 及以上）。

## 3. 查看审查结果

「运行记录」→ run 详情（或 PR 详情页），自上而下：

1. **发现的问题**——标题/位置/原因/依据/修复建议分列。来源标注区分：
   - `precheck`（静态规则）：确定性规则命中，附规则说明；
   - `reviewer`（模型发现）：模型实际输出（是否已执行取决于部署是否启用 LLM 第二阶段——未执行会如实标注，不冒充）。
2. **建议怎么改**——建议补丁（统一 diff，逐文件着色）。补丁是**版本化**的：
   页面/复制/下载/发布统一取 `active` 版本；若有修正，原始失败版本保留可追溯（`correction_of` 链）。
3. **验证了什么**——见下节，**务必区分三分**。
4. **下载**：Markdown 报告 / JSON / `.patch`（下载的就是检查所验证的同一版本，文件头含 digest）。

## 4. 理解验证结果（本产品最重要的阅读能力）

**验证三分，通过≠通过≠通过：**

| 分项 | 回答的问题 | 状态语义 |
|---|---|---|
| ① 格式与路径检查（结构级） | diff 格式合法、触及文件在变更集内？ | 通过 ≠ 可应用 |
| ② 真实可应用性 | 对准确 head 的 `git apply --check` 实测过吗？ | 五态：**通过 / 失败 / 未执行 / 未验证（环境不可用）/ 陈旧**；证据按补丁 digest 绑定，补丁更新后旧证据自动失效 |
| ③ 实际修复测试 | 在隔离副本中：修复前测试失败 → 应用补丁 → 修复后测试通过？ | 需部署方预配置测试命令（`MU_FIX_TEST_CMDS`）；**未执行会如实标注** |

记忆口诀：**可应用 ≠ 行为正确；模型评估通过 ≠ 测试通过；未执行 ≠ 不适用**。
「未验证（环境不可用）」属如实呈现（如 clone 失败），不会误报为通过，稍后可重试。

## 5. 审批修复（仅维护者）

1. P0/P1 发现会产生**逐条具名审批票**（「审批」页；带 finding/位置/head/有效期）。
2. 逐票批准或驳回：**run 内全部 P0/P1 票批准后**修复轮才启动（没有"全部批准"捷径）；
   任一票驳回 / 过期 / head 已变化（STALE）→ 该 run 进入 BLOCKED（fail-closed）。
3. 修复轮是 **dry-run**：产出建议补丁与验证证据，**不写远端**。

常见票状态：`PENDING` 待决定 / `APPROVED` 已批准（修复启动后变 `CONSUMED`）/ `REJECTED`
已驳回 / `EXPIRED` 超时 / `STALE` head 已推进——后三类终态后**永不自动恢复**，需要新 head 重新审查产生新票。

## 6. 发布审查评论到 PR（仅维护者）

入口：run 详情产物面板「预览并发布到 PR」。

1. **预览**（只读）显示：目标平台与 PR、审查所用 head、**远端当前 head**、**写入身份**
   （MergePilot GitHub App 机器人 / MergePilot Gitee 机器人——不是你的个人账号）、评论全文。
2. 点「确认发布」才真正写出。发布权限与审批同权（`decide_review`，仅 maintainer）；
   后端为最终授权方。
3. 幂等语义：同一 run 重复发布 = **原位更新**机器人自己的既有评论（不刷屏、不覆盖人工评论）。
4. head 已推进 → 拒绝发布（409 `head_moved`）：陈旧结论不发布，PR 更新后重新审查获得新结果。

## 7. 常见状态速查

| 状态 | 含义 | 处理 |
|---|---|---|
| 无发布按钮/置灰 | 当前角色无 decide_review | 用维护者账号；按钮下方有具体原因 |
| 「历史运行，仅查看」 | 产物面板默认显示最新 run | 发布需要最新 run——点「查看最新 run」 |
| head 已变化，拒绝发布 | 远端已推进，结论基于旧版本 | PR 更新后重新审查 |
| 可应用性「未验证（环境不可用）」 | 检查环境不可用，如实不误报 | 稍后重试；不影响其余产物 |
| 修复测试「未执行」 | 部署未配置预批准命令 | 找管理员按 DEPLOY-GUIDE 配 `MU_FIX_TEST_CMDS` |
| 补丁「不可应用」 | 真实 git apply 失败（含修正尝试） | 参考失败原因；原始版本保留可追溯 |
| 模型审查未执行（EGRESS_DENIED 等） | 出站策略/同意/白名单未就绪 | 找平台管理员，见 TROUBLESHOOTING「T-MODEL」 |

## 8. 应用修复与合并（预告：开发中）

「机器人提交修复 commit → 新 head 自动重审 → CI 结果消费 → 人工确认合并」为**开发中能力**，
本版本不可用。当前闭环止于：审批 → dry-run 修复轮 → 建议补丁 + 验证证据 → 人工发布评论。
届时以版本公告与本指南更新为准。
