# 12 · 工程化路线评审与部署拓扑（2026-09-17）

> 背景：五轮真实运行（R1/R2/R3-TRACED/RAG-TRACED/V3-TRACED）交付后，对"MergePilot 生产化"的
> 工程路线评审。评审对象：团队工程化设计草案（Webhook 触发 + 前后端分离 + RBAC + PostgreSQL）。
> 结论：**方向可行；四处关键修订后可按草案推进**。部署拓扑定案：**镜像收敛为 3 个，
> docker-compose 单命令交付多容器，不合并 Agent 进单容器**。

## 一、对设计草案的四项修订

### 修订 1（最重要）：Agent 底座路线必须先定——推荐复用 AgentTeams 底座

草案把 Agent 层画成 "Reviewer/Fixer/Verifier 三个框直连 API"，掩盖了最重的架构决策：

- **路线 A（推荐）**：生产部署直接复用 AgentTeams 底座（controller + Matrix + MinIO + 网关 +
  copaw 运行时），新 Server 只做 GitHub 桥接与人工门 UI。角色分离、消息审计、文件同步、
  停等恢复（consumer 空闲唤醒、sync token 重建）这些**已被五轮运行验证的基础设施原样保留**，
  MVP 2-3 周的估算才成立。
- **路线 B**：拆成轻量无状态 Agent 服务。工程上更"干净"，但角色契约执行、Matrix 审计链、
  工具护栏、停等恢复全部重造——工期 ×2 以上，且丢掉差异化（多角色对抗结构 + 全链留痕
  正是系统对评委/客户的核心价值）。

### 修订 2：可观测性层是必建项，不是可选项

生产设计必须保留并产品化：每 Agent 轮次的 OTel span 直连（v3 已含跨 Agent traceparent 关联、
会话 ID、工具 genai 语义）、**按 PR 的成本护栏**（失控 Agent 循环是真金白银；按 PR/按轮设预算
上限与熔断）、证据包自动归档。这层是产品对客户的核心承诺，不进图就是把它留在图外。

### 修订 3：凭据隔离要写成架构不变式

Agent 会执行 shell、clone、跑测试——生产必须保留：每任务独立容器、网络策略（worker 仅可达
网关/控制器/GitHub 只读）、tool-guard 开启，以及一条不变式：**Fixer/Verifier 进程内不存在
任何 push 凭据**。五轮"零 GitHub 写入"从来不是提示词约束，是凭据不存在。合并只能由人点击。

### 修订 4：PR force-push 会让审查作废——版本绑定必须复用已有实现

PR 生命周期图缺"审查进行中 PR 被更新"的分支。已有实现可直接复用：demo 平台后端的
人工门已绑定 `(verification_id, head_sha)`，版本过期/换头返回 409（STALE_VERSION /
REJECTED_TERMINAL 语义已验证）。这是改造项，不是新建项。

## 二、部署拓扑定案（回答"是否合成一个 docker"）

**结论：不合并。** 镜像收敛为 3 个，交付形态为 docker-compose 单命令多容器：

```
docker-compose.yml（单命令交付）
├── mergepilot/server   [新建]  Webhook 桥 / API / PostgreSQL / 审批 UI 后端
├── mergepilot/ctrl     [已有]  agentteams-embedded：控制器 + Matrix + MinIO + 网关
│                                （按 Worker CR 动态创建/销毁 worker 容器——现机制）
├── mergepilot/worker   [已有]  同一镜像 × N 个容器，角色由 CR/env 区分
│                                （copaw-worker + agentloop v3 层 + RAG hook 可选层）
├── mergepilot/web      [可选]  Element Web / 操作台前端
└── .env / secrets              凭据注入；worker 内无 push 凭据
```

**不合并的四个理由（全部是安全/工程要求，不是习惯）：**

1. **沙箱隔离**：Reviewer/Fixer 执行的是**不可信 PR 代码**（clone、跑测试、PoC）。独立容器
   保证一次逃逸/事故不波及控制面与其余角色；合并进单容器 = 一次逃逸全栈沦陷。
2. **凭据分离**：每个 worker 只持有自己的 Matrix 账号、网关 consumer key、FS 前缀；
   合并容器则全部凭据同域，违背角色/凭据分离的审计承诺。
3. **生命周期分离**：worker 由控制器按 CR 动态创建/销毁（五轮运行反复验证），可按角色
   独立重启、未来按并行波次横向扩容；单容器无法单独重启一个角色。
4. **故障隔离**：五轮运行中 worker 级故障（agent 异常、sync token 损坏、端口冲突）都被
   限制在单容器内，未波及控制面。

**镜像数不是容器数**：4 个 Agent 共用**同一个 worker 镜像**，角色差异由 CR/env 注入——
"4 个 Agent"在打包上只对应 1 个 worker 镜像 + 1 个 ctrl 镜像 + 1 个前端镜像（可选）。
K8s/Helm 仅在多团队多仓部署（V3+）时引入，单团队交付 compose 足够。

## 三、PR 生命周期（生产版，含修订）

```
开发者提 PR / 更新 PR
    ↓ Webhook（绑定 head_sha；force-push → 旧审查作废 STALE）
Reviewer Agent 自动审查
    ├─ 无风险 → 标注 "safe to merge"，通知维护者（合并仍由人点击）
    ├─ HIGH → 人工门停等（审批走 IM/操作台；决策按授权模式投递）
    │   ├─ 批准 → Fixer（仅改标记文件·测试冻结）→ Verifier 独立验证
    │   │   ├─ PASS → 标注 "verified, ready to merge" → 维护者手动合并
    │   │   └─ FAIL → 重试 ≤2 次（新 task id，禁复用事务号）→ 升级人工
    │   └─ 拒绝 → REJECTED · BLOCKED · 证据归档（终态，不可翻转）
    └─ CRITICAL → 同 HIGH，但只报告不修复
全程：按 PR 预算护栏 · span 直连 OTel · 证据包自动归档 · Agent 无 push 凭据
```

## 六、边界与不变式（重申）

1. 零 GitHub 写入：Agent 无 push 凭据；合并按钮由人点击。
2. CRITICAL 只报告不修复。
3. 证据等级不混用：REAL_EXECUTED / CONTROL_PLANE_MECHANISM / SYNTHETIC / NOT_EXECUTED 分开标注。
4. 演示平台（离线证据回放）与生产 Server 是**两个产品形态**：前者继续服务竞赛/复盘，
   不并入生产服务；生产是新部署单元，复用的是运行时与流程资产，不是回放器代码。
