## 二、案例设计：同一任务贯穿 Reviewer → Fixer → Verifier → Controller

### 任务（一个任务，一次贯穿）

**任务编号 `run-elem-20260915-01`**：测试仓 `nghqqa/fastapi-boilerplate-demo`（专用于验证的测试仓库，非生产仓）新建分支 `mergepilot/rework-refund-20260915`，任务 = **实现 `refund(order_id, amount)` 部分退款并修复金额校验缺陷**：

- 分支基线放入 `app/payments.py`（含一个真实缺陷：重复退款未按 `refund_id` 幂等，金额校验用浮点比较）与**验收测试** `tests/test_refund_acceptance.py`（见下）。
- **预固定的验收测试**（运行前提交、全程禁止修改、Fixer 不可见修改指令）：
  1. 合法部分退款成功且落账；
  2. 退款金额 > 原支付金额 → 拒绝（整数分比较，无浮点误差）；
  3. 同一 `refund_id` 二次提交 → 幂等（不重复落账）；
  4. 金额边界：0 与负数 → 拒绝。
- Reviewer 的 kickoff 消息（模板 §0）必须给出：风险依据（金额校验/幂等/精度三类）、验收条件（上述 4 条测试名）、运行次数上限。**不允许**在 kickoff 中给出任何补丁或具体实现。

### 角色与真实性约束

| 角色 | 动作 | 约束 |
|---|---|---|
| Reviewer（真实模型） | 给出风险依据与验收条件，转发任务 | 输出不得由预写文本替代；`rework_case/attempt1|attempt2` 只是机制层夹具，**不**作为本次模型输出 |
| Fixer（真实模型） | 在分支上生成修复提交 | 真实模型输出；**不保证第一次失败**——若一次通过，如实记录为 first-pass PASS，不篡改测试制造返工 |
| Verifier（真实模型 + 真实执行） | 独立运行 `python -m unittest tests.test_refund_acceptance`（在干净 checkout 的 head_sha 上） | 裁决只能来自测试的真实退出码与输出；每轮给出 `VERDICT=PASS/FAIL` + 测试报告路径 |
| Controller（返工触发） | 第一层：AgentTeams leader 依据 Verifier 的 FAIL 把任务退回 Fixer（带退回原因）；第二层（可选）：MergePilot PG 控制器消费同一事件，状态机退回并留痕 | 退回消息由系统/leader 发出，**不得人工伪装成 Worker 发言**；人工审批走已实现的权威入口（票据审批 UI/API，不在房间口头放行） |

### 次数上限与升级

- fix 尝试 ≤ 3、verify 运行 ≤ 3（与控制器 `MAX_VERIFY_ATTEMPTS=3` 一致）；第 3 次 FAIL → **HOLD / 升级人工**，记录升级原因。所有尝试（含 PASS 与 FAIL 的完整测试输出、每个 head_sha）全部保存，不丢弃失败尝试。

### 故障注入场景（可选 Scenario B，明确标注）

目的：真实模型的返工次数不可控；为**确定性演练"FAIL → 退回 → 修复 → 重验"链路**，允许在 Fixer 第 1 次提交后由操作员执行**一次**标注式注入：在房间以 `[FAULT-INJECTION]` 前缀公告后，向分支追加一行"环境注记"使验收测试 #3（幂等）在 Verifier 的运行中确定性失败（例如临时在测试仓 checkout 中放置一个与幂等键冲突的预置行，仅影响该次运行）。注入点、目的、撤销方式在公告与证据中逐字记录；Fixer 随后须在**不修改验收测试**的前提下让全部 4 条测试通过。若不授权 Scenario B，则只运行 Scenario A（纯真实，可能 0 次返工）。
