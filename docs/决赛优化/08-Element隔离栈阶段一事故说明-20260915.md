## 四、接入有效凭据前阻断自动调用的最小方案（仅方案，未实施）

前提事实：当前 ctrl 已停止=网关不存在=**天然零调用**（最强阻断已就位，保持停止即可）。以下为"未来需要 ctrl 运行但凭据无效/未接入"时的最小阻断：

- **修改对象（唯一）**：本栈 Higress AI 路由 `default-ai-route` —— 在启动 ctrl **之前**通过控制台 API 删除（DELETE）。控制器只做"向已存在路由授权消费者"（`AuthorizeAIRoutes`），**不创建路由**；无路由时该操作为空操作（源码），阻断不会被打开。
- **效果与实证**：所有模型路径请求落控制台兜底 404，**零上游接触**——本次事故中 13:37–13:56 的 19 分钟已实证该状态（219 次请求、0 上游、0 计费）。控制器探测将按源码以 WARN+5s requeue 空转（无害、无外部接触）。
- **不推荐**：从 allowedConsumers 摘除消费者（ctrl 运行期会被 reconcile 秒级加回，不稳定）；仅清空 provider tokens（转发行为不确定，可能仍产生供应商侧接触）。

## 五、preflight 能否独立执行（任务 3 结论：有条件可以；系统级承诺收回）

- **命令本身**：agt llm-preflight 是纯客户端 HTTP 调用，不触控制器 API、不唤醒任何 CR；"该命令 ≤3 请求"对**命令自身**成立（已证实）。
- **"一次命令=系统最多 3 请求"**：**收回**。已被事故证伪——命令 1 请求的同时，常驻组件独立产生 3 次上游请求。
- **经网关的 preflight 能否不唤醒 Manager/Worker**：在 ctrl 运行的默认状态下**不能**（manager CR 自动引导 + 5s 探测循环是常驻调用方）。**唯一可实现隔离窗口的时序**（需授权后另行设计验证）：先启 ctrl（路由不存在→探测 404 空转）→ 用**诊断专用消费者**创建路由且 allowedConsumers 仅含该消费者 → 立即以诊断 key 执行 preflight（唯一被授权调用方；manager/worker 的调用在 key-auth 边界 401=零上游）→ 事后以访问日志核验窗口内上游请求仅来自 preflight → 最后再授权 manager/worker。**已知风险**：路由创建不触发 CR reconcile，窗口在无 CR 事件时稳定；但若期间发生任何 CR 事件，控制器会重新授权 manager 使窗口塌缩——故该窗口是"设计的验证时序"，不是机制保证，必须以日志事后证实。
- **不依赖栈的替代**：ctrl 停止时可用临时容器（`docker run --rm`，镜像自带 agt）直连 `https://api.deepseek.com` 做 key 预检——零常驻调用方、命令级 ≤3 请求严格成立；但它**不验证网关路由路径**，且临时容器属声明清单外资源，需单独授权。
