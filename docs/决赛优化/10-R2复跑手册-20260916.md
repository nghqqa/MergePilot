## 一、审计教训 → 复跑对策(逐条)

| R1 的坑 | R2 对策 |
|---|---|
| 事务号幂等:门后重派复用 `delegate-<taskid>`,无新事件 | 全新 project/task id(`pr2r2-review-1/fix-1/verify-1`),无历史 txn 可撞;**若中途需要作废,禁止复用同 task id 重新委派**(改用 `-alt` 后缀新任务) |
| Reviewer SPEC 点破漏洞类别 | SPEC 只指向 diff 与新增文件,不写 "../ / file read" 等结论性字眼;PR 标题与文件名自带意图,Reviewer 仍能独立发现 |
| 离席 6.3h 空烧 ~70 次/3.97M | 全程守候;门决策用交互问答当场完成;若等待超过 10 分钟,先停 leader(heartbeat 源) |
| 门后操作员直接驱动 Fixer | 门批准后操作员**只发门决策消息**,委派由 Leader taskflow 完成;以团队房出现新委派事件为唯一开工信号 |
| consumer 空闲收不到委派 | 委派发出 60s 内未消费 → @mention 唤醒;必要时重启目标 worker(先例已验证) |
| 指令文件时滞 | 播种 MinIO → 确认同步(`grep <run_id> ~/task/PR-METADATA.md`)→ 再发 kickoff |

## 三、R2 的验收口径

- 门批准后,团队房存在**新的** fix 委派事件(≠ 任何被作废事件的 ID)——这是与 R1 的本质差异;
- Fixer 开工时间晚于该事件且无操作员执行指令介入;
- Reviewer 结论未由 SPEC 预设(SPEC 文本作为证据一并归档);
- 墙钟 ≤40 分钟;用量与费用如实记录(不再有离席项)。
