# 复赛材料约束

> 状态：材料基线。它约束后续 PPT、PDF、代码包说明、Demo、视频字幕和答辩口径，不代表对应交付物已经完成。

## 1. 官方必交材料

### 1.1 更新版项目方案

- **是否必交：**是。
- **形式：**PPT / PDF。
- **必须覆盖：**根据初赛反馈更新场景闭环、架构、Skill 设计、风险边界和落地计划。
- **必须展示：**完整场景链路、样例输入输出、日志、Trace、指标、评测结果和自动化验证证据。
- **工程内容：**工具、MCP、RAG、可观测集成、接口 Schema、数据流、部署配置、失败处理、权限、审批、回滚和审计机制。
- **开放内容：**开放或开源计划及其真实完成状态。

### 1.2 可执行 AgentTeams 代码包

- **是否必交：**是。
- **形式：**仓库链接或压缩包。
- **必须包含：**运行入口、依赖说明、配置文件或模板、样例输入输出和运行证据。
- **交付标准：**评委能够根据文档判断支持平台、完成安装检查并启动 Demo；不能依赖开发者口头补充隐藏步骤。

### 1.3 可运行 Demo / Demo 视频

- **是否必交：**是。
- **形式：**在线体验、本地部署或视频演示。
- **必须覆盖：**至少一条完整场景链路，能够验证 Agent 协作、工具调用、输出结果、异常处理、执行证据和关键技术亮点。
- **现场要求：**入围后的路演、专家问答、测试要求和展示规范以组委会后续通知为准。

## 2. 材料生成时点

在以下条件稳定前，不冻结最终复赛 PPT 和视频：

- Preview 阻断缺陷已经处理并形成明确裁决；
- Windows 侧控制台访问、离线安装、生命周期和清理合同稳定；
- 最终代码提交、Release 版本和安装包 SHA 已冻结；
- Demo 使用的运行证据、状态投影和截图均有可追溯来源；
- 测试计数和真实性边界经过最终复核。

当前可以维护逐页底稿，但不得把开发中状态写成最终能力。

## 3. 架构统一口径

### 3.1 Agent 与 Skill

复赛材料统一使用：

> **4 个运行时 Agent 承载 6 类职责，确定性控制器驱动交接。**

四个运行时 Agent 是 Manager / Coordinator、Reviewer、Fixer、Verifier。初赛中的 Triage 和 Fix Planner 是逻辑职责；当前工程实现将它们分别收敛到确定性 Skill、规划阶段和控制器状态机，不为保持数字而新增无独立边界的 Agent。

如需保留六张职责卡，必须把 Triage 标为 `Skill Stage`，Fix Planner 标为 `Planning Stage`，不能继续把二者标成已部署 Worker。

### 3.2 控制面

- Workflow Controller 是流程状态权威，不计入 Agent 数量。
- Agent 负责语义判断；Skill 负责有 Schema、deadline 和 fail-closed 合同的工程执行。
- Policy Gateway 负责授权与最小权限决策。
- GitHub MCP 只执行经过治理的工具调用，不承担流程状态权威。

### 3.3 Sidecar 术语

- 不使用“可观测侧车”描述当前整体审计与 Trace 架构；统一写作**审计与可观测平面**。
- 不使用“MCP sidecar”描述 GitHub MCP；统一写作**GitHub MCP 隔离服务**。
- 只有组件与主应用处于同一部署和生命周期单元时，才可使用 sidecar。

### 3.4 数据与可观测

- PostgreSQL：任务状态、阶段转换、Outbox、审批与结构化审计。
- pgvector：案例检索。
- MinIO：按实际已冻结用途描述，不与 PostgreSQL 合并成笼统的“数据层已验证”。
- 本地 Trace、OTel、SLS 必须分别陈述完成状态；不得用其中一项的证据替代另一项。

## 4. 真实性约束

以下边界在权威证据更新前必须逐字保持：

```text
application_integration_verified=false
database_verified=false
production_verified=false
revision_producer_contract=NOT_VERIFIED
audit_producer_contract=NOT_VERIFIED
direct_routing_verified=false
transport_profile=wsl-user-relay
```

材料必须区分以下状态：

- **已实现：**代码存在且通过约定的静态或单元门禁。
- **已验证：**存在对应环境、版本、输入、输出和可复算证据。
- **Preview 验收：**只证明声明的 Preview 环境和范围，不等于生产验证。
- **待验证：**已有设计或实现，但缺少目标环境证据。
- **规划：**尚未实现，只能放在路线图。

禁止使用“生产可用”“生产验证完成”“全链路全部验证”等超出证据范围的表述。

## 5. 声明与证据规则

每个可验证声明至少绑定：

1. 功能或合同名称；
2. 精确 Git commit 或 annotated tag；
3. 测试或真实运行环境；
4. 原始 evidence 路径或 Release 资产；
5. 通过计数或稳定错误码；
6. 已知限制与未验证边界。

PPT 可以使用短结论，但逐页底稿和声明证据矩阵必须提供完整指针。历史证据必须标明日期和当时版本，不得当作当前环境状态。

## 6. 版本与数字规则

- Release、安装包、PPT、视频字幕和 README 中的版本、commit、测试计数必须来自同一冻结清单。
- 不硬编码开发过程中的临时 SHA；展示时引用最终 manifest 或发布 tag。
- Agent 数量、Skill 数量、阶段数、路由边数量和测试计数不得跨版本拼接。
- 截图中的状态必须来自真实投影；合成失败态只能明确标为生产投影函数派生的演示夹具。
- 初赛材料作为历史快照保留，不回改成当前实现，也不让当前实现迁就初赛数字。

## 7. 安全与隐私

- 不在 PPT、视频、截图、日志、压缩包或 evidence 中出现 PAT、PEM、Matrix、MinIO、数据库密码、Cookie 或配置秘密正文。
- 不暴露个人用户名、主机名、绝对机器路径、私有 IP 或未脱敏 room / user 标识。
- 展示配置时使用模板、字段名、哈希或 `<redacted>`，不展示真实值。
- GitHub PAT 的统一口径是：**仅进入 GitHub MCP 隔离服务，Worker 不持有 PAT。**

## 8. Demo 约束

- 主演示采用一条稳定、可重复的完整链路；不在现场临时开发或修复环境。
- 同时准备真实 complete、failed、stale 三种投影，用于展示正常结果、首个稳定错误和陈旧数据处理。
- 明确哪些画面是历史真实运行证据，哪些是当前实时状态。
- 网络、WSL 或外部服务不可控时使用预先录制的视频和冻结证据，不伪造实时成功。
- 演示脚本必须包含异常处理、回滚或 fail-closed 证据，而不只展示成功路径。

## 9. 材料变更规则

- 本文件是复赛材料口径的上游约束；修改关键架构或真实性口径时，应同步复核所有下游材料。
- 项目功能开发与复赛材料编辑分开提交，避免证据 SHA 与文字修订混在同一提交中。
- 最终提交前执行一次跨材料一致性检查：版本、数字、术语、真实性边界、链接和截图来源必须一致。
