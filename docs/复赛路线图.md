## 二、里程碑(按推荐顺序)

### M1.5 · 任务隔离(per-task room)— ✅ 已验证(2026-07-25)

**起因**:M1 验证时 worker 房间累积多个 PR 历史 → 上下文粘滞 → reviewer 卡 PR#5;每次验证功能要重建 worker,太重。需要任务隔离。

**方案**:每个 PR 建专属 Matrix 任务房间 → OpenClaw 按房间隔离 session(已验证 sessions.json key = `agent:main:matrix:channel:<room_id>`)→ 零跨-PR 污染。admin 以真 @mention 胶囊驱动 worker(不靠 manager 中转)。

**验证(2026-07-25)**:
- ✅ **worker join 任务房间**:干净(重建后)的 worker 配 `autoJoin: always` + `groupAllowFrom: [admin, manager]`,2 秒内自动 join 外部脚本建的任务房间。(之前「不 join」是旧 worker 被上下文污染卡住,非框架策略限制。)
- ✅ **worker 响应 admin 真 @mention**:plain text 不行,`formatted_body` + `m.mentions` 的真 mention 胶囊才行(worker 只认 mention 胶囊,不认纯文本 @)。
- ✅ **全链路在隔离房间跑通**:iso5-pr6 任务房间,reviewer→fixer→verifier 全程经 v2 watcher 的 @mention 驱动(零人工 nudge),verifier 裁定 `blocked-needs-approval`(L2 HOLD)。
- ✅ **零跨-PR 污染**:每个 PR 独立房间 = 独立 session;不再需要重创 worker。

**关键结论(纠正之前的误判)**:
- 之前以为「worker 不 join 外部房间 = HiClaw 安全策略不可改」——**错了**。干净 worker join 正常;`autoJoin`/`groupAllowFrom` 可改(openclaw.json),且不是限制因素。
- 真正的两个技术点:① OpenClaw session 按房间隔离(自动,白拿);② worker 只响应**真 @mention 胶囊**(formatted_body + m.mentions),不响应纯文本 @ —— v2 watcher + submitter 都用真 mention。

**工具产出**:
- `tools/handoff_watcher_v2.py` + `start-watcher-v2.sh`:动态发现房间(含新建任务房间)+ 在任务房间里 @mention 下一阶段 worker。
- `tools/submit_pr_taskroom.py`:建任务房间 + 邀请 reviewer/fixer/verifier/manager + 发 @reviewer mention 任务。
- `tools/create_task_room.py` + `post_mention.py` + `room-recent.py`:底层建房/发 mention/查房间消息。
- `tools/light-reset-sessions.sh`:已验证**无效**(worker 从房间历史 resync)。

**已知小瑕疵**:① v2 watcher log 字符串有笔误(把阶段名硬编码为 "verify"),不影响逻辑;② worker 偶发重复发 TASK_COMPLETED → watcher 多次 @mention(功能无碍,可按 stage 去重);③ 被 context 粘滞污染的旧 worker 可能不 join 新房间 → 需确保 worker 干净(重建或全新)。

- **目标**:一次提交 → review→fix→verify→(merge/hold) 全程无人工 nudge。
- **验收标准**:提交 PR 后,全链路无任何人工 nudge,出最终裁定。
- **结果(2026-07-25 干净环境 e2e)**:PR#6 一次提交,watcher 驱动全部 3 个交接(reviewer→fixer→verifier→裁定),**零人工 nudge**;fixer 自主创建真实 PR#7,verifier 裁定 `blocked-needs-approval`(L2 HOLD,策略正确)。
- **关键结论**:
  - ⚠️ **SOUL 状态机单独不够**:Manager 即便有显式「收到 TASK_COMPLETED 立即派下一阶段」约束,仍在 review 后停(「通知 admin,rest 一下」)——LLM 编排本质不可靠,不能依赖。
  - ✅ **确定性 handoff watcher 是正解**:`tools/handoff_watcher.py` 常驻 manager 容器,轮询 worker 房间,检测 `TASK_COMPLETED` 自动 nudge manager 推进。正则对真实消息全量命中;干净环境(全新 worker/房间)跑通全链路。
- **已知小瑕疵(非阻断,后续可优化)**:① worker 偶发重复发 TASK_COMPLETED → watcher 对同一阶段发多次 nudge(功能无碍,可按 stage 去重);② fixer 复用 `fix/security-demo` 分支名导致 PR#7 mergeable=dirty(改用唯一分支名即可)。
- **复现**:`tools/start-handoff-watcher.sh`(起 watcher)+ `tools/nudge.sh` 提交 PR 任务 + `tools/run-room-recent.sh <agent>` 观察。

### M2 · verify-fail 自动回滚 【多 Agent 协同 25% + 工程落地 20%】
- **目标**:verifier 判 FAIL 时,Manager 自动触发回滚(不再脚本手动)。
- **任务**:
  1. Manager SOUL 加 verify-fail → rollback 自动分支。
  2. 把 `rollback-release-candidate.sh` 逻辑接进 Manager 自动执行(revert + 关 PR + 写 audit)。
  3. 跑负向场景(坏修复)验证。
- **验收标准**:提交一个会 FAIL 的 PR,verifier 判 FAIL 后 Manager 自动 revert + 关 PR + 审计,**无人干预**。
- **预期证据**:自动回滚 run trace + revert commit + `audit_events` 新增 rollback 记录。
- **工作量**:1 天(逻辑已验证,只差接进 Manager)。

### M3 · 实时可观测(OpenTelemetry GenAI) 【工程落地 20% + 可观测推荐】
- **目标**:post-hoc trace → 实时 Trace(span 树)+ Metrics(token/延迟)。
- **任务**:
  1. agent / 网关层埋 OTel GenAI span。
  2. 后端:AgentLoop / LoongSuite,或自存(PG/Tempo)。
  3. 看板接实时数据(替换/并行 make_dashboard 的静态版)。
- **验收标准**:一次 run 产生实时 OTel trace + metrics,可在看板实时看到 span 树与 token/延迟。
- **预期证据**:OTel trace 导出(JSON)+ metrics 截图 + 实时看板。
- **工作量**:2–3 天(本路线图体量最大,放 M1/M2 后专注做)。
- **依赖**:无强依赖;接 AgentLoop 需对应文档/凭证。

### M4 · 量化评测(benchmark) 【工程落地 20%,「科学量化」】
- **目标**:从单 demo → 数据集级量化指标。
- **任务**:
  1. 构造/收集 N(≥10)个 PR,覆盖 L0/L1/L2 各风险等级 + 各 finding 类别。
  2. 跑闭环,统计:成功率、修复耗时、token 成本、RAG 召回准确率。
  3. 出评测报告。
- **验收标准**:N≥10 PR 的指标表(成功率/平均耗时/token/召回准确率),附原始数据。
- **预期证据**:benchmark 报告(md + 数据表)+ 原始 run 产物。
- **工作量**:1–2 天。

### M5 · 官方 SLS Skill(`alibabacloud-sls-query`) 【Skill 工程 25% + 可观测数据源】
- **目标**:兑现承诺的官方 Skill,且 SLS 即可观测数据源。
- **任务**:
  1. 阿里云账号开通 SLS + 取 AK。
  2. 封装为 Skill / MCP(verifier 按 TraceId 查 SLS 日志)。
  3. 验证:verifier 调用后把 SLS 查询结果写入 verify 证据。
- **验收标准**:verifier 经该 Skill 查到 SLS 日志并引用进 verify 报告。
- **预期证据**:SLS 查询结果截图 + verify 报告中的引用 + Skill 契约(附录 B 更新)。
- **工作量**:1 天。
- **依赖**:**阿里云账号**(需提前准备)。

### M6 · Skill 再实测 + RAG 进生产形态 【Skill 工程 25%】
- **目标**:Skill 实测 2/11 → ≥4/11;RAG 从 host 侧 → agent 在环调用。
- **任务**:
  1. 实测 `TestRunner`(CI 或隔离容器跑测试,verify 阶段真跑)。
  2. 实测 1 个(`DiffParse` 或 `RiskClassify` 独立封装)。
  3. RAG 封成 hiclab-net 上的 HTTP/MCP 服务,让 agent 真在环里调。
  4. RAG 评测集扩到 N 条,出准确率。
- **验收标准**:新增 ≥2 Skill 有实测证据;RAG agent 在环调用成功 + 扩展集准确率报告。
- **预期证据**:新 Skill 实测报告 + RAG 服务 + 评测报告(去掉「5 条小样本」限定)。
- **工作量**:2–3 天。
