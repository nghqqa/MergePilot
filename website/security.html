安全加固清单

内建安全基线（默认已生效）

  • 会话 Cookie：HttpOnly + Secure + SameSite=Lax——明文 HTTP 上不传输；
  • 管理面 CSRF 双提交校验；未认证一律 401/403，同形响应不泄露细节；
  • webhook HMAC-SHA256 验签 + delivery 一次性去重（重复投递幂等）；
  • platform_admin 不可经邀请授予（API/claim/DB 三层拒绝）；
  • secrets 仅存环境变量与 keystore，绝不入库、入日志、入审计；
  • 数据库/keystore/模型卷不发布端口（仅内部网络可达）。

部署侧必须项：两种公网暴露拓扑

MergePilot 默认仅在本机回环暴露两个端口：127.0.0.1:48500（Console 管理面 + OAuth + 全量 API） 与 127.0.0.1:48590（webhook-ingress，仅放行 POST /api/mu/github/webhook 与 GET /api/health）。请按团队网络条件二选一，切勿直接裸露 48500 或以明文 HTTP 承载会话：

拓扑适用场景公网暴露面说明
拓扑 A：单域名 HTTPS 团队共用 异地/多成员需浏览器 OAuth 登录与接受邀请 https://你的域名 统一终止 TLS；Webhook 路径分流至 48590，Console 与 OAuth 路径转发至 48500 最常见团队方案；反代层必须配限流与 HTTPS 301
拓扑 B：最小暴露面分离（推荐高敏内网） 成员均在公司 VPN / Tailscale / 内网访问 Console 公网仅暴露 48590（GitHub Webhook）；48500 仅限内网/Tailscale HTTPS 访问 公网完全不可达 /multiuser 与其余 /api/*

生产反向代理模板（Nginx）

以下为拓扑 A 的完整生产模板（含 HTTP→HTTPS 301、请求头透传、Webhook 分流与限流）。若采用拓扑 B， 删除 location / 块或将其改为 return 404;，仅保留 webhook 与 health 即可：

# 放在 http {} 块内：限流区定义
limit_req_zone $binary_remote_addr zone=mp_api:10m rate=60r/m;
limit_req_zone $binary_remote_addr zone=mp_webhook:10m rate=120r/m;

server {
    listen 80;
    server_name mp.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name mp.example.com;
    ssl_certificate     /etc/letsencrypt/live/mp.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mp.example.com/privkey.pem;

    add_header X-Content-Type-Options nosniff always;
    add_header X-Frame-Options DENY always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;

    # GitHub Webhook → 转发至 webhook-ingress (48590)
    location = /api/mu/github/webhook {
        limit_req zone=mp_webhook burst=30 nodelay;
        proxy_pass http://127.0.0.1:48590;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 如使用 Gitee Webhook：48590 默认只放行 GitHub webhook，Gitee 须直转 48500
    location = /api/mu/gitee/webhook {
        limit_req zone=mp_webhook burst=30 nodelay;
        proxy_pass http://127.0.0.1:48500;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 管理面与 OAuth API（拓扑 B 最小暴露面时删去以下两个 location）
    location /api/ {
        limit_req zone=mp_api burst=20 nodelay;
        proxy_pass http://127.0.0.1:48500;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        proxy_pass http://127.0.0.1:48500;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

生产反向代理模板（Caddy，自动申请 TLS）

mp.example.com {
    @gh_webhook path /api/mu/github/webhook
    reverse_proxy @gh_webhook 127.0.0.1:48590

    # 拓扑 A：同时暴露 Console 与 OAuth（含 Gitee webhook）
    # 拓扑 B（仅暴露 GitHub Webhook）时，把下面一行改为 respond 404
    reverse_proxy 127.0.0.1:48500
}

无公网 IP 场景：Cloudflare Tunnel 最小配置

若部署机位于内网/NAT 后且无公网 IP，可使用 Cloudflare Tunnel（cloudflared）将 HTTPS 入口安全打通至本机回环端口：

# ~/.cloudflared/config.yml（拓扑 A 示例；仅暴露 Webhook 时删去最后一条通配规则）
tunnel: <YOUR_TUNNEL_ID>
credentials-file: /etc/cloudflared/<YOUR_TUNNEL_ID>.json

ingress:
  - hostname: mp.example.com
    path: ^/api/mu/github/webhook$
    service: http://127.0.0.1:48590
  - hostname: mp.example.com
    service: http://127.0.0.1:48500
  - service: http_status:404
  1. 防火墙：仅放行反代 80/443 端口；48500 / 48590 保持 127.0.0.1 回环绑定；数据库端口不对任何外部网络开放。
  2. 限流不削弱验签：反代层限流（API 60 req/min/IP、Webhook 120 req/min/IP）与后端 HMAC-SHA256 验签叠加生效。

secrets 纪律

  • .env 与 App 私钥权限 0600，不入 git（仓库 .gitignore 已覆盖 .env）；
  • 轮换：CONSOLE_SESSION_SECRET（全会话失效重登）、 keystore（rotate API，旧 key 即刻失效、新 key 即刻生效）；
  • 日志与审计设计上不含 secrets（webhook 审计仅记 delivery 前缀与 kind）。

审计与可观测

  • 登录/邀请/成员变更/webhook 处理/事件消费全量审计落库；
  • cchain 信任链状态变化（READY/BLOCKED）留痕；
  • /api/health 的 version 字段即运行版本真源。

基础镜像 CVE 处置

  • 策略：基础镜像按 digest 钉定（禁浮动 tag）；alpine 仓库发布修复而基础快照滞后时，构建期 apk --no-cache upgrade 显式拉取闭合（幂等）；
  • CVE-2026-85091（zlib）：rc.35.6-rc2 起闭合；
  • CVE-2026-111497（brotli 解码器越界写）：rc.35.6-rc8.4.1 双面闭合——基础镜像前移至含 node 22.23.4 的 node:22-alpine（node 内置 brotli 面，apk 无法修，只能钉定 digest 前移）+ brotli-libs 1.2.1-r0（libcurl/git fetch 链路面）；防复发回归锁入 CI（root 探针断言，非 root 探测失败不作为修复证据）；
  • 边界：trivy 不覆盖 node 二进制内置 brotli，node 版本须以镜像内 root 探针（scripts/verify-image-security-fixes.cjs）或 node --version 实测为准，不能只依据扫描结果宣称修复。

升级安全

升级前 pg_dump；镜像按 digest 拉取（不用浮动 tag）； 升级窗口内 consumer 停止期间的投递会在恢复后由 GitHub 重投（幂等）。
